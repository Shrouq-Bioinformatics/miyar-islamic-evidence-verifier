# مِعيار — ملف المشاركة

## بطاقة مختصرة

| البند | البيان |
|---|---|
| الاسم | مِعيار — مدقّق الأدلة الإسلامية |
| المسار | **المسار الرابع: أدوات المعرفة والتحقق لتمكين المعرّفين بالإسلام** |
| الجمهور | فرق المحتوى الدعوي والتربوي، المحررون، والمراجعون |
| النطاق | فرز أولي قابل للتتبع قبل النشر، لا فتوى ولا اعتماد نهائي |
| حالة النسخة | نموذج عامل مع AI واسترجاع وحفظ مشترك؛ لا يدعي فتوى أو دقة علمية |

## المشكلة

تنتقل ادعاءات إسلامية إلى مواد دعوية وتعليمية مع إحالات ناقصة أو خلط بين النص والتفسير والرأي والفتوى. البحث اليدوي بطيء، وواجهة «إجابة واحدة» قد تخفي غياب المصدر. يحتاج الفريق إلى مسار يجيب أولًا: هل لدينا دليل مسترجع فعلًا؟ ما درجة كفايته؟ ومتى يجب إيقاف النشر وإحالة الحالة إلى مختص؟

## الحل والقيمة

مِعيار مساحة عربية RTL تستقبل الادعاء كما ورد، وتعرض حالة الدليل والخطوة التالية، وتحفظ قرار المراجع في مساحة الفريق المشتركة. التصميم المقصود يفصل أربع طبقات:

1. **الادعاء والسياق** كما أدخلهما المستخدم.
2. **الاسترجاع والمطابقة** مع مقتطف منقح يحمل مرجعًا ورابطًا وطبعة وتاريخ استرجاع.
3. **الفرز الأولي** إلى مدعوم مبدئيًا، يحتاج مراجعة، أو أدلة غير كافية.
4. **القرار البشري** قبل الاعتماد أو النشر.

القيمة الأساسية ليست «الإجابة الأسرع»، بل جعل لحظة التوقف وعدم اليقين واضحة وقابلة للمراجعة.

## ما هو منفذ الآن

- لوحة قيادة، نموذج تدقيق، سجل حالات، غرفة مراجعة، مكتبة مصادر، تحليلات وإعدادات أمان.
- API عند `POST /api/verify`.
- فهرس أدلة منقح مع استرجاع مقتطفات ومرجع ورابط وطبعة وتاريخ استرجاع.
- تحليل AI رسمي عبر بوابة Replit المُدارة، مع تصفية معرفات المقتطفات غير المسترجعة.
- حفظ الحالات وقرارات المراجعة في PostgreSQL؛ تبقى تفضيلات العرض المحلية في `localStorage`.

## المنهجية

### المسار الحالي

1. التحقق من طول المطالبة.
2. استرجاع مقتطفات من corpus منقح بمطابقة عربية محافظة.
3. إرسال المطالبة والسياق والمقتطفات فقط إلى نموذج AI المُدار.
4. تصفية المراجع التي يعيدها النموذج إلى معرفات المقتطفات التي استُرجعت فعلًا.
5. عرض المقتطف والمرجع والرابط والطبعة وتاريخ الاسترجاع، ثم حفظ النتيجة للمراجعة البشرية.

### مسار AI والاسترجاع الحالي

يرسل الخادم الادعاء والسياق والمقتطفات المسترجعة إلى نموذج `gpt-5.4-mini` عبر بوابة OpenAI المُدارة في Replit، ويطلب JSON مقيدًا. لا يقبل الخادم معرفًا إلا إذا كان ضمن المقتطفات المسترجعة، ويعرض النص والمرجع والرابط والطبعة وتاريخ الاسترجاع. النتيجة فرز أولي مساعد وليست فتوى أو تحققًا علميًا نهائيًا.

### المنهجية المستهدفة قبل التجربة الميدانية

استرجاع نصوص موثقة ومؤرخة → مطابقة الاقتباس والسياق → إظهار المقطع والرابط والنسخة → فرز محافظ → مراجعة بشرية مزدوجة للحالات الحساسة → حفظ قرار وسجل تدقيق.

## القيود والمخاطر

- corpus الاسترجاع الحالي محدود بثلاثة مقتطفات منقحة؛ لا ينبغي تعميم النتيجة على كل القرآن والحديث والفتاوى.
- لا مجموعة اختبار محكمة ولا نتائج دقة/استدعاء/اتفاق مراجعين.
- الأرقام والبذور الظاهرة في الواجهة للعرض، وليست قياسات تشغيلية حقيقية.
- الحالات وقرارات المراجعة محفوظة في PostgreSQL لمساحة فريق افتراضية؛ لا تزال المصادقة والأدوار وسجل التدقيق غير القابل للتلاعب غير منفذة.
- لا تسجيل دخول، أدوار، صلاحيات فرق، عزل مستأجرين، أو إدارة جلسات.
- CORS مفتوح في الخادم الحالي، ولا توجد ضوابط إنتاجية للحد من الطلبات.
- لا سياسة احتفاظ منفذة ولا آلية حذف مركزي؛ مسح بيانات الموقع يحذف السجل المحلي.
- رابط العرض العام متاح: `https://maayr-islamic-evidence-verifier.replit.app`، لكن آخر تغييرات workspace تحتاج إعادة نشر قبل التسليم.
- مستودع GitHub العام: https://github.com/Shrouq-Bioinformatics/miyar-islamic-evidence-verifier
- العربية ولهجاتها، اختلاف الطبعات، صحة الحديث، والسياق الفقهي تحتاج خبراء ومصادر مرخصة.

## بروتوكول التقييم المقترح — لم يُنفذ بعد

1. **مجموعة ذهبية:** 120–200 حالة مجهولة المصدر للنظام، موزعة بالتساوي على آيات محددة، أحاديث منسوبة، أسئلة فقهية معاصرة، تعميمات بلا مصدر، وحالات ملتبسة/مضللة.
2. **الترميز:** مراجعان مستقلان من أهل الاختصاص يحددان الحالة، المرجع المقبول، سبب الإحالة، وخطورة الخطأ؛ يحسم ثالث الخلاف.
3. **خط أساس:** البحث اليدوي المعتاد للفريق، مع قياس الزمن وجودة الإحالة.
4. **اختبار أعمى:** ترتيب عشوائي، دون إظهار التصنيف الذهبي، وفصل بيانات الضبط عن الاختبار.
5. **مؤشرات:** دقة الإحالات النصية، استدعاء حالات «يحتاج مراجعة»، معدل الدعم الزائف، معدل الامتناع، الوسيط الزمني للوصول إلى إحالة قابلة للتتبع، واتفاق المراجعين (Cohen’s κ).
6. **بوابة أمان مقترحة:** صفر إحالة مختلقة في مجموعة الاختبار، واستدعاء ≥95% للحالات الحساسة، ومراجعة بشرية لـ100% من الفتاوى/المسائل المعاصرة. لا يُعلن رقم نجاح قبل تنفيذ القياس وتوثيقه.
7. **اختبارات إساءة:** حقن أوامر، اقتباس مبتور، تشابه أسماء السور/الأحاديث، لغات مختلطة، وبيانات شخصية داخل المطالبة.

## الخصوصية والتعامل مع البيانات

### الواقع الحالي

- النتائج تحفظ في PostgreSQL لمساحة العمل؛ تفضيلات الواجهة فقط في `localStorage`.
- يرسل الخادم المطالبة والسياق والمقتطفات المسترجعة إلى بوابة OpenAI المُدارة؛ لا توجد الآن شاشة موافقة تفصيلية أو حذف مركزي.
- لا مصادقة؛ أي شخص يستخدم ملف المتصفح نفسه قد يرى البيانات المحلية.
- يجب استخدام بيانات عامة/مصطنعة فقط، وعدم إدخال أسماء أشخاص، محادثات خاصة، معلومات صحية، أو أسرار.

### ضوابط مطلوبة قبل النشر

موافقة صريحة قبل الإرسال الخارجي، تقليل البيانات وتنقيح PII، تشفير أثناء النقل وعند التخزين، أدوار وصلاحيات، مدد احتفاظ وحذف، سجل تدقيق، اتفاقية معالجة مع المزود، تحديد الإقليم، واستجابة للحوادث. ينبغي توثيق مصادر النصوص وتراخيصها ونسخها.

## إعادة الإنتاج والنشر

المتطلبات: Node.js 24 وpnpm.

```bash
pnpm install --frozen-lockfile
pnpm run typecheck
PORT=24752 BASE_PATH=/ pnpm --filter @workspace/miyar-evidence-verifier run build
pnpm --filter @workspace/api-server run build
```

تشغيل الخدمات وفق artifact router في Replit:

```bash
PORT=8080 pnpm --filter @workspace/api-server run dev
PORT=24752 BASE_PATH=/ pnpm --filter @workspace/miyar-evidence-verifier run dev
```

تتوقع الواجهة `/api/verify` على الأصل نفسه؛ لذا يحتاج التشغيل خارج Replit إلى reverse proxy يجمع الواجهة و`/api`. يحتاج الخادم `DATABASE_URL` ومتغيرات Replit AI Integration. لا تُضمّن أي مفتاح في كود أو أرشيف. النشر العام الحالي autoscale على `https://maayr-islamic-evidence-verifier.replit.app`، لكن يجب إعادة نشر آخر تغييرات workspace ثم إعادة اختبار الرابط من نافذة خاصة.
